# Agent Note: Models 页面声明模型是否接受图片

Status: implemented

[English](2026-09-07-model-editor-image-modalities.md) | 中文

## 问题

Models 页面过去可以配置 pi-ai 行的 id、显示名称、上下文窗口与输出上限，却不能配置该模型是否接受图片。适配器早已按「条目 `input` 列表 → 已安装目录条目 → 路由 `defaultInput`」解析（见[路由默认输入模态](../architecture/2026-08-12-pi-ai-route-default-input-modalities.zh.md)），也就是说该能力在 settings 文档中已经存在；只是手工声明提供方的页面无法表达它。动因正是该页面自身的场景：一个提供视觉模型的 OpenAI 兼容网关经**添加自定义提供方**加入后报告为纯文本，而读取模态的三处准入点——模型选择、提示词准入与 `read_image`——会拒绝该图片，并建议选择一个用户在该页面根本无法创建的图片能力模型。

承载行内额外字段的折叠区当时也被标为**容量**，一旦有别的内容加入，这个名称就不再描述它的内容。

本 Agent Note 推翻了上文「没有任何配置界面编辑 `input`」的决策，并保留它的其他决策——尤其是解析链——继续有效。

## 决策

行内的「高级」折叠区新增**接受图片**复选框：勾选写入 `input: [text, image]`，取消勾选写入 `input: [text]`。

**两种状态都显式写入，而不是在关闭图片时删除该字段。** 列表缺失时会去问下一级——目录条目，再到路由的 `defaultInput`——而默认接受图片的路由随后就会为这个刚被用户声明为纯文本的模型重新放行图片。这正是过度声明的一侧：提示词准入会在提供方有机会拒绝之前就把图片持久化，而同一个误声明的模型在之后每一条仍携带该图片的请求上都可能再次失败。`[text]` 把用户的答案写在解析链最先读到的地方。

**自身未作声明的行显示为未勾选。** 页面只持有草稿行，本该作答的目录条目与路由默认值在这里读不到——容量占位符早已接受同样的限制。因此取消勾选是一种声明，而不是对路由此前行为的断言。

**折叠区改名为「模型详情」。** 两个编辑器共用这段文案，而 DeepSeek 目录编辑器里的内容——两个容量——仍是模型的详情，因此一个名称同时适用。

**DeepSeek 目录编辑器保持不变。** 该适配器的图片条目还带有按模型的请求限制（`imagePixelBudget`、`imageMaxBytes`），本页面并不编辑它们；在那里声明图片而不带限制会让这项能力半配置化，而官方路由本就自带其视觉条目。

## 考虑过的替代方案

**取消勾选时删除 `input`。** 拒绝：缺失意味着「先问目录，再问路由」，于是纯文本声明会悄悄放宽为路由默认所允许的值——正是显式写入所要防止的失败——而且该控件在这种路由上根本无法表达纯文本。

**三态控件（继承／纯文本／图片）。** 拒绝：继承状态无法如实显示，因为它解析到的目录条目与路由默认值在本页面读不到。一个第三个选项读作一种含义却实际表示另一种的控件，比一个只声明本行答案的控件更糟。

**提供方级的能力开关。** 拒绝：模态是按模型的属性，同一条路由上的模型对它的答案并不一致，因此提供方级的控件只可能被设成某些行会拒绝的值——这也是推理等级不在卡片上可编辑的原因。

## 后果

自定义提供方上的视觉模型只需一个复选框，三处准入点随后就会在该模型上放行图片。该声明仍未经验证：声明为图片能力而网关只提供文本的模型，会在提示词准入之后被提供方拒绝，持久图片仍留在会话日志中，恢复方式是改正声明或改选纯文本路由。

手写的 `input` 列表会保留到用户切换该行时为止，因为行内补丁会先展开已存储的条目再应用控件带来的变更。页面现在会在字符串与计数之外写入一个数组值字段。
